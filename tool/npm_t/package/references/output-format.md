# 输出格式与展示规范

## 通用响应结构

`music` / `auth` / `install` 等"上游 API 类"命令输出标准 JSON 结构：

```json
{
  "errcode": 0,
  "errmsg": "",
  "data": { ... },
  "status": 1
}
```

**响应状态判定**:
- **成功判定只看 `errcode == 0`**——这是 Agent 唯一可信的成功依据
- `data` 包含实际业务数据
- `status: 1` 是上游接口调用状态提示，**仅作辅助参考**（部分上游错误响应里 `status` 可能不是 1，但仍由 `errcode` 决定 CLI 成功与否）
- **`control` 命令不走这个结构**——它透传酷狗客户端本地 HTTP 协议的原始 JSON，成功字段通常是 `code` 而不是 `errcode`。见 [references/control.md](./control.md)

## 展示规范

向用户展示结果时，**必须遵循以下规范**：

### 1. 歌曲/歌单列表展示（批量优先用表格）

> **强制规则**：结果 ≥ 2 条 → 表格；结果 = 1 条 → 单行链接（按客户端可用性决定是否加链接）。

#### 1.1 客户端可用性探测（前置条件）

**首次**要向用户展示歌曲列表、歌单列表或歌单内歌曲列表之前，**必须**先探测本机是否有可用的酷狗客户端（详见 [SKILL.md#5-首次要展示歌曲歌单前探测本机客户端可用性](../SKILL.md)）：

```bash
kugou-cli control detect
```

根据退出码记下 `client_available`：

| 退出码 | 含义 | `client_available` |
|---|---|---|
| `0` | 已安装 | `true` |
| `1` | 探测出错（注册表权限等） | `false`（按没客户端处理） |
| `2` | 没装客户端 | `false` |

**会话内只探测一次**，后续展示复用本次结果。`control detect` 是零副作用探测，不会启动客户端、不会抢焦点。

#### 1.2 规则总览

| 结果条数 | 展示形式 | 客户端可用？ | 歌曲名/歌单名是否加链接 |
|---|---|---|---|
| **≥ 2** | Markdown 表格（**必须**） | 无关 | **一律不加**（保持列宽整洁） |
| **= 1** | 单行 Markdown 链接 | 是 | **不加**（可直接走 `control play`） |
| **= 1** | 单行 Markdown 链接 | 否 | **必须加**（用户手动打开） |
| **= 0** | 自然语言提示 | 无关 | 不适用 |

#### 1.3 表格格式（结果 ≥ 2 条）

**歌曲列表**（来自 `search` / `recommend guess|similar|text` / `charts` / `favorites` / `recent` / `playlist-songs`）：

```markdown
| 序号 | 歌曲名 | 歌手 |
|------|--------|------|
| 1 | 晴天 | 周杰伦 |
| 2 | 七里香 | 周杰伦 |
| 3 | 稻香 | 周杰伦 |
```

**歌单列表**（来自 `search-playlist` / `recommend-playlist`）：

```markdown
| 序号 | 歌单名 | 创建人昵称 |
|------|--------|------------|
| 1 | 周杰伦经典30首 | 酷狗小编 |
| 2 | 慢摇车载DJ | DJ阿圣 |
```

**硬性规则**：

- 表格单元格里的歌曲名/歌单名**不加** Markdown 链接——加了会让列宽自适应 URL，可读性反而变差
- 表格里也不列 `play_link` / `song_list_url` / `mix_song_id` / `global_id`——这些字段是给后续 `control *` 命令用的，由 agent 内部持有，**不展示给用户**
- 序号从 1 开始连续递增
- 如果返回总条数 > 表格展示条数（例如 `search` 默认 20 条），**只展示实际返回的那部分**，不要截断也不要用省略号

#### 1.4 单条结果格式（结果 = 1 条）

**有客户端时**（`client_available = true`）—— 歌曲名/歌单名**不加链接**：

```markdown
晴天 - 周杰伦
```

```markdown
周杰伦经典30首 —— 酷狗小编
```

**无客户端时**（`client_available = false`）—— 歌曲名/歌单名**必须加链接**：

```markdown
[晴天 - 周杰伦](https://www.kugou.com/mixsong/xxxx.html)
```

```markdown
[周杰伦经典30首](https://www.kugou.com/songlist/xxxx.html)
```

#### 1.5 为什么表格不加链接？

- 表格的目标是**浏览/筛选**，不是立即跳转；用户在表格里通常要做的是"挑一首播放"或"挑一个歌单打开"，而非"挨个点开"
- 加链接会让列宽按 URL 自适应，中文长字符串场景下整张表可读性急剧下降
- ID（`mix_song_id` / `global_id`）由 agent 内部持有，等用户明确说"播放第 3 首" / "打开第 2 个歌单"时再走 `control play` / `control play-playlist` 或浏览器跳转

#### 1.6 反例（禁止）

| 禁止 | 错误原因 |
|---|---|
| 表格里写 `[晴天](https://...)` 形式的可点击单元格 | 列宽爆炸、可读性差 |
| 表格里把 `play_link` / `global_id` 也单列出来 | ID 是 agent 内部数据，不该展示给用户 |
| 结果 ≥ 2 条却用列表式 `[歌名 - 歌手](link)` 堆叠 | 表格才是 ≥ 2 条的标准形式 |
| 单条结果（= 1）时仍用表格 | 杀鸡用牛刀，单行更直接 |
| 单条无客户端时不加链接 | 用户没有客户端可控制，必须给链接让用户手动打开 |
| 单条有客户端时仍加链接 | 既然有客户端可以直接 `control play`，加链接反而多余 |
| 不探测就硬性决定加不加链接 | 必须先 `control detect`，不能凭猜测 |

#### 1.7 control 操作响应不受本节约束

`control play` / `control favorite song` 等**操作响应**不包含 `play_link`，按 control 协议原始 JSON 字段原样展示即可（见 [references/control.md](./control.md)）。本节规范只适用于 `music *` 命令返回的列表类结果。

### 2. 统计数据

提取关键字段并以结构化方式呈现（如"累计听歌 342 首，时长 22.4 小时"）

### 3. 二维码

使用 `qrcode_img_url` 渲染给用户：Markdown `![酷狗登录二维码](<qrcode_img_url>)`，让客户端拉取并渲染

### 4. 错误展示

- CLI 错误输出到 **stderr**，stdout 只放原始 JSON（或原始 body）
- Agent 解析失败时同时检查：退出码（0 = 成功，非 0 = 失败）、stdout body 的 `errcode` 字段、stderr 输出
- 不要把 stderr 输出原样展示给用户；转化为自然语言说明（如"账号登录过期，请重新登录"）

### 5. 推荐理由（主动推荐场景必写）

**触发条件**：仅当 agent **主动**给用户推荐歌曲时才写推荐理由，包括以下命令的返回结果：

- `kugou-cli music recommend guess`（猜你喜欢）
- `kugou-cli music recommend similar -s <song>`（相似推荐）
- `kugou-cli music recommend text --text <描述>`（文本推歌）
- `kugou-cli music charts <rank_id>`（榜单，详见 [music.md#7](music.md#7)）
- `kugou-cli music recommend-playlist`（歌单推荐）—— 歌单本身就是主动推荐行为

**不触发**：用户**主动搜索**（`search` / `search-playlist`）、查自己数据（`favorites` / `recent` / `stats`）、查指定歌单内容（`playlist-songs`）的结果**不写**推荐理由——用户来找东西，不需要再被解释一遍。

#### 写法要求

在歌曲列表**之后**追加一段 Markdown 引用块（`>`）作为推荐理由，必须包含以下三层信息：

1. **整体歌曲风格**：用一句话概括本批推荐的整体风格/情绪基调（例如「以华语流行慢歌为主，情绪偏舒缓治愈」）。
2. **匹配逻辑**：依据当前推荐场景说明匹配来源——
   - 猜你喜欢 / 歌单推荐 → 「基于你的听歌偏好/历史播放」
   - 相似推荐 → 「延续《XXX》的 XXX 风格/主题」
   - 文本推歌 → 「贴合你描述的『XXX』场景」
   - 榜单 → 「来自 XXX 榜第 N 名，XXX 类热度风向」
3. **挑 2-3 首解读**：从本批返回中挑选 2-3 首，**结合行业认知**（歌手常见风格、歌曲广为人知的标签、所属专辑/年代等）做一句解读，帮助用户判断是否合口味。

> ⚠️ 解读内容**仅基于歌名 + 歌手名调用 agent 自身行业认知**，不要捏造歌词、不要引用未经验证的曲风标签。如对歌曲不熟悉，宁可写得笼统一些也不要硬编细节。

#### 字数硬约束

**总字数控制在 220-260 字（含标点）**。超出或不足都需要重写到区间内。撰写时不必分段，整体作为一段引用块即可。

#### 输出示例

```markdown
> 为你挑选了 5 首华语流行慢歌，整体偏舒缓、情绪内敛，节奏不快不躁，编曲以钢琴和原声吉他为主，更适合午后或深夜一个人安静循环。匹配逻辑来自你最近的播放记录和猜你喜欢数据，我们从中挑出与历史偏好契合度最高的几首组成了这张清单。其中《晴天》是周杰伦 2003 年的代表作，校园民谣的底色配钢琴铺陈，几乎成了一代人的青春共同记忆；《七里香》延续了同期的中国风与诗意意象，副歌弦乐层层推进，听感最为饱满宏大；《稻香》则把视角拉回乡村童年，节奏轻快但内核温暖，是整张清单里最治愈的一首作品。
```
